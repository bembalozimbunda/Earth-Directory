## 6. Deep Technical Analysis: Service Worker (`sw.js`), `dev-dist` & System Resurrection Protocol

### A. Root-Cause Analysis: Why Service Workers "Killed" Development Environments
During iterative full-stack development, modern web applications running inside sandboxed containers or iframes (such as Google AI Studio, Cloud Run, or Vite Dev Containers) can experience sudden "dead system" states (white screens, frozen browser tabs, failed module imports, or endless spinner loops).

#### The 3 Root Failure Modes Identified:
1. **`dev-dist/sw.js` Precache Hash Mismatch**:
   - When `vite-plugin-pwa` is configured with `devOptions: { enabled: true }`, Vite compiles and emits a development service worker into `/dev-dist/sw.js` along with Workbox runtime scripts (`workbox-*.js`).
   - In development mode, Vite continuously compiles code into dynamically hashed unbundled ES modules. However, the Workbox service worker precaches `index.html` referencing specific historical chunk hashes.
   - When the dev server restarts or code changes, the service worker intercepts browser `fetch` requests and continues serving the *stale precached HTML*, which attempts to fetch non-existent historical Vite chunk hashes, triggering uncaught 404/504 errors and freezing execution.
2. **Iframe Origin Scope Trapping**:
   - Because preview environments run within a scoped origin iframe, an active service worker controls all network traffic for that origin. Even if the dev server restarts, the browser's `ServiceWorkerRegistration` stays alive in the browser's persistent cache storage.
3. **Workbox Network-First / Stale-While-Revalidate Deadlock**:
   - If dynamic API endpoints (`/api/heartbeat`, `/api/sadc/telemetry`, `/api/universities/registry`, `/api/zambia/tribes`) are caught by overly broad glob patterns (`globPatterns: ['**/*.{js,css,html...}']`), the service worker responds with cached synthetic 200/404 responses instead of routing directly to the active Express server.
